The Limit May Not Be in the Model

By Josiah Hunter•September 2, 2026•9 min read

A product ceiling can look like model behavior from the outside, but the useful question is where the stop was imposed and whether that layer still has a current reason to impose it.

You encounter the limit as a product event. A run stops early. An agent refuses to continue. A tool loop ends at the same count every time. A response is shorter than the task appears to require. From the outside, it looks as though the model reached its limit.

Sometimes it did. You do not know that from the product event alone.

The model is one participant in the behavior you see. A request can cap output or tool calls. A runner can stop an agent loop. A host can decide which capabilities to expose. A protocol can require negotiated features. Compatibility rules can preserve old defaults. Safety, latency, cost, and resource controls can intentionally hold a boundary in place after the model improves.

A persistent limit tells you where to investigate, not what verdict to reach.

Trace the Layered Path

Start with the observed ceiling and work inward.

Observed product ceiling &nbsp;&nbsp;| &nbsp;&nbsp;v Product interface or host policy &nbsp;&nbsp;| &nbsp;&nbsp;v Protocol or session contract &nbsp;&nbsp;| &nbsp;&nbsp;v Agent orchestration layer &nbsp;&nbsp;| &nbsp;&nbsp;v API request configuration &nbsp;&nbsp;| &nbsp;&nbsp;v Model capability &nbsp;&nbsp;| &nbsp;&nbsp;v Current constraints: compatibility, safety, latency, cost, protocol, resource protection

That direction matters. Starting at the model can hide a nearer layer that already explains the stop. Starting at the product event lets you distinguish “the model could not” from “the system did not let it.”

Model Capability Is Narrow Evidence

Model capability can change substantially. OpenAI's April 14, 2025 GPT-4.1 launch post documented a context window of up to one million tokens, compared with 128,000 tokens for previous GPT-4o models in that publication's comparison Introducing GPT-4.1 in the API. This is dated evidence that a specific capacity expanded. It does not establish that every longer product workflow should expand with it.

The publication distinguishes simple needle retrieval from harder long-context work. It says its more complex multi-round long-context evaluation remained difficult even for advanced reasoning models Introducing GPT-4.1 in the API. A larger context window can remove one constraint while reliability, latency, interaction quality, cost, and surrounding contracts remain unresolved.

When a ceiling looks older than the model's current capacity, the improvement gives you a reason to inspect that ceiling. It does not give you permission to delete it.

A Request Can Masquerade as Model Capacity

Inspect the request that was actually sent before attributing the result to the model.

In the OpenAI Responses API, max_tool_calls caps the total built-in tool calls processed in one response. The API reference describes it as a response-wide cap and says further model attempts are ignored after the threshold Create a model response.

That is a request-layer limit.

Suppose a trace shows the model attempting another built-in tool call after the configured max_tool_calls threshold, and the API ignores it. For that run, the stop belongs to the request or API layer. This does not prove that raising the cap would produce a better answer, preserve latency, or reduce user friction. It establishes only that the observed stop occurred before model capability became the explanation.

Output length has the same distinction. The Responses API exposes max_output_tokens as an upper bound covering visible output tokens and reasoning tokens Create a model response. If a product repeatedly returns short responses, a configured output ceiling is one possible cause. Confirm it with the actual request, response metadata, trace, or logs. A repeatable ceiling created by max_output_tokens still says nothing by itself about what the model could otherwise generate.

A Runner Can End the Loop

Agent products place an orchestration layer between the request and the model.

The OpenAI Agents SDK documentation describes a runner that repeatedly invokes the model and tools. It also documents MaxTurnsExceeded, which is raised when the configured max_turns is exceeded, and says setting max_turns to None disables that runner limit Running agents.

When a run ends with MaxTurnsExceeded, you have direct evidence that the runner stopped at its configured threshold. You do not yet have evidence that the model could not continue.

Because the SDK allows the limit to be disabled without changing the model, the orchestration boundary is easy to identify. That does not make it obsolete. The limit may bound cost, interrupt an unproductive loop, protect latency, or keep the user experience predictable.

The supported conclusion is smaller and more useful: a configurable runner ceiling can be distinguished from an intrinsic model limit. Assess the model's capability separately from the safety and utility of changing the ceiling.

Hosts and Protocols Shape What Users Can Reach

A limit can also reside in the host, interface, or protocol contract around the model.

MCP revision 2025-06-18 makes these layers visible. Its elicitation specification allows implementations to choose their interface pattern. The protocol does not prescribe a particular interaction layout or question count Elicitation. A product's elicitation pattern therefore does not automatically come from MCP or the model. The implementation may have chosen it.

The same versioned specification restricts elicitation schemas to flat objects with primitive properties. It excludes nested objects and arrays of objects to simplify client implementation Elicitation. A model may be able to produce richer structure than the active interface contract accepts. The contract still constrains the exposed behavior.

The MCP 2025-06-18 architecture specification assigns the host responsibility for orchestration, permissions, security-policy enforcement, authorization, context aggregation, LLM integration, and related coordination Architecture. Host policy can shape the user's experience before model capability becomes the limiting factor.

The session contract adds another boundary. Under MCP 2025-06-18, clients and servers negotiate capabilities and use only those successfully negotiated for the session Lifecycle. A model may be capable of an action while the active session cannot expose it because the related application capability was not negotiated.

These examples do not identify the cause of an unspecified product's behavior. They show how interface choice, schema restrictions, host policy, and session negotiation can each impose a ceiling independently of the model.

An Old Default May Still Be a Current Contract

Finding the layer is only half the diagnosis. You still need to determine whether the limit has a present rationale.

Backward compatibility can preserve a stale-looking default. Google's AIP-180 guidance treats changing a static API default as a breaking change that must not occur within a minor version for APIs governed by that guidance AIP-180: Backwards compatibility. It also says API-visible behavior or semantics should not change when the change is likely to break reasonable user code AIP-180: Backwards compatibility.

AIP-180 is not a universal rule for every product. It documents a concrete compatibility mechanism. Consumers can build around a default through client code, tests, budgets, alert thresholds, pagination assumptions, review processes, or user workflows. A technically larger value can still break those expectations.

The model may have outgrown a default while the API contract has not. Changing it then requires a compatibility decision, not just a code edit.

Governance Can Delay Exposure Deliberately

Capability and exposure are separate decisions.

OpenAI's April 15, 2025 Preparedness Framework update says covered systems reaching its High capability threshold require safeguards that sufficiently minimize severe-harm risk before deployment. It also describes review and recommendations from a Safety Advisory Group Our updated Preparedness Framework. This is a scoped OpenAI governance example from 2025, not a general description of every deployment.

A model or system can cross a capability threshold before a product exposes that capability broadly. The controlling layer may be a safety gate, review requirement, deployment policy, abuse-prevention control, or release process.

If a ceiling persists because of a governance decision, removing it is a policy change. Calling it a refactor would hide the decision that actually needs review.

Resource Protection Is a Current Rationale

An unbounded system can be a production risk.

MCP revision 2025-06-18 recommends per-request timeouts. It also says implementations should enforce a maximum timeout even when progress notifications arrive, limiting the impact of misbehaving clients or servers Lifecycle. The maximum remains useful because a peer can misbehave.

Other fixed ceilings may protect latency, spend, availability, or other users. A timeout, turn cap, token cap, recursion limit, queue limit, or tool-call budget can be a deliberate control. It can also be an old default that nobody has reconsidered. The constant alone cannot distinguish the two.

A turn budget, recursion limit, predefined route, layer of glue code, sprawling configuration surface, manually maintained threshold, or strict output contract tells you where to investigate, not what verdict to reach. These boundaries do not establish that a constraint is obsolete, trace it to an earlier model limitation, or justify removing it.

Four Tests for the Ceiling

Once you have traced the stop to a plausible layer, apply four tests to establish what you know.

First, establish provenance. Find the source of the limit. A named API parameter, runner exception, host policy, protocol rule, compatibility document, or deployment gate is stronger evidence than a repeated user-visible pattern. Provenance extends beyond the file containing a constant. It includes the decision record, configuration owner, release note, or contract that explains why the value exists.

Next, identify the present rationale. A limit created for an older model's context window may deserve review after a model upgrade. One created for cost, latency, safety, abuse prevention, or compatibility may still apply. If nobody can state the rationale, you have evidence of process decay. You do not yet have evidence that removal is safe.

Then demonstrate the relevant model capability outside the product ceiling. The GPT-4.1 context-window example shows the necessary restraint. A dated capacity increase can be real without proving that a longer interactive workflow will be reliable, useful, safe, or economical. Test the behavior you intend to expose, not a nearby benchmark.

Finally, find the dependent contracts. Public API semantics, client assumptions, timeout budgets, billing expectations, monitoring thresholds, safety reviews, protocol negotiation, and host permissions may all depend on the current ceiling. A small implementation change can still alter a cross-system contract.

These are diagnostic tests, not a remediation sequence. They separate an obsolete default from a current control and expose the cases where the evidence remains incomplete.

Name the Layer, Then Judge the Limit

A configured request explains a request-layer stop. In the Responses API, max_tool_calls and max_output_tokens are documented examples, limited to those parameters and that API.

A runner condition explains an orchestration-layer stop. In the OpenAI Agents SDK, MaxTurnsExceeded identifies the documented runner behavior, not an intrinsic inability of the model to continue.

An active contract can explain an interface or protocol ceiling. MCP 2025-06-18 provides version-pinned examples involving interface choice, elicitation schema shape, host responsibility, and negotiated session capabilities.

A governing compatibility policy can explain why a default or visible behavior remains fixed. AIP-180 supplies a scoped example for APIs governed by that guidance.

A safety review, deployment safeguard, timeout, cost control, latency bound, or abuse-prevention measure can explain a governance or resource ceiling.

None of those explanations can be inferred from the constant alone. You cannot conclude that the architecture fell behind, that the model is the blocker, or that deletion is safe.

Limits are easy to find. The difficult part is preserving the distinction between an obsolete default and a justified control after model capability changes. Treat every constant as an investigative lead. Model improvement does not justify deleting it while compatibility, safety, latency, cost, protocol, or resource requirements may still supply its current rationale.
