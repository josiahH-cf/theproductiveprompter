The Model Release Experiment

By Josiah Hunter•October 2, 2026•4 min read

TLDR

  • Every trial receives the same user-prompt bytes: PRINT-SHOP CHALLENGE v1.0.
  • The protocol preserves one original response for each model and settings profile, including failures and unavailable states.
  • Recorded settings show the requested configuration. They do not independently verify how much internal reasoning occurred.
  • Each response is an individual field observation, not a universal model ranking or proof that a setting caused a difference.
  • This introduction has no campaign results. Model cards, run pages, and saved results will be attached only after publication is verified.

The frozen challenge

PRINT-SHOP CHALLENGE v1.0 is the fixed artifact at the center of the experiment. The frozen challenge asks for a 600–800 word story, a JSON receipt, and a public notice of at most 80 words.

The scenario starts with an $80 materials budget and 120 machine minutes. Before production, the materials budget falls to $66. The response must also account for a fixed $35 expense while tracking the contribution toward a $220 repair goal. A possible $100 donation remains uncommitted at the end of the story, so it cannot be treated as confirmed income.

These details are the task, not background decoration. Together, they test how each response handles narrative requirements, numerical constraints, a revised plan, structured data, and a short public update. This article will not solve the challenge or suggest an order plan because either choice would change the artifact before the trials begin.

The user prompt remains byte-identical across trials. The draft records its SHA-256 as d6ea22391915e294a6ed80dc109550b035cf7c9548159dc71d0efc39e661f96d, but the exact frozen prompt bytes were not available for independent recomputation here. The value must be recomputed before publication.

Fixing the user prompt does not make every provider environment identical. Native instructions and CLI behavior can differ. The protocol therefore records the model, settings profile, and provider environment separately from the common user-facing challenge.

What changes between profiles

The experiment preserves one original response for each model/settings profile. The main profiles change one factor at a time, creating a local comparison with the relevant baseline. Trials that combine settings belong to a separate factorial mode.

If two preserved responses differ, that difference can be described. One response from each profile cannot show that the changed setting caused it, and it cannot support a broad conclusion about the model.

The available controls also differ by provider. Where the selected model and client support them, the Codex configuration reference documents reasoning effort and a separate optional Responses API verbosity override. The documented verbosity values are low, medium, and high.

Claude Code’s model configuration documentation describes a per-session effort control for compatible models. Its effort levels are calibrated per model, so matching labels do not establish equal amounts of reasoning across models. Organization controls can also cap a requested effort level. A stored request for high effort is evidence of the requested client configuration, not independent proof of how much internal reasoning occurred.

Verbosity needs a separate distinction. Claude Code’s @@AF0@@ flag controls diagnostic logging. It is not a native response-verbosity setting comparable to Codex’s documented output control.

These documentation claims were checked on October 2, 2026. They should be checked again at publication because model and client capabilities can change.

What the evidence can support

A preserved output records one field observation: this model, in this provider environment, with this requested profile, returned this response to the frozen prompt.

That record can show whether the required parts appeared, how the response represented its receipt, and whether the run failed. It cannot establish general model quality, produce a universal ranking, or prove that a setting caused an observed difference.

Preservation also covers inconvenient outcomes. Original responses remain unpolished. Failures stay recorded as failures. If a model is unavailable, the experiment records that state instead of silently replacing it.

Official documentation can identify candidates, but a catalog listing does not verify access through the experiment account. Claude’s supported-model documentation lists models supported by Claude Code, but that listing does not verify access through the experiment account.

For example, the official Codex model documentation lists GPT-5.3-Codex-Spark as retired on September 14, 2026 and unavailable in the ChatGPT desktop app, Codex CLI, and IDE extension. If Spark appears in the candidate set, the experiment must preserve that unavailable state. A successor cannot stand in for it.

This keeps three kinds of evidence separate. Documentation can describe a model or control. Account checks determine whether the configured account can use it. The preserved run records what was requested and what actually happened.

Why there are no results here

This is the protocol article, published before the campaign runs. It contains no campaign findings, verified account-access results, rankings, costs, usage figures, or live results pages. Candidate documentation and planned profiles do not supply any of those results.

After publication is verified, the controller is intended to check for missing trials and attach the saved results. The resulting model cards, individual run pages, and results section will place the frozen prompt beside the settings and original output needed to interpret each observation.

For now, PRINT-SHOP CHALLENGE v1.0 remains the fixed artifact introduced at the start: a prompt awaiting preserved responses, not a source of results that do not yet exist.
